# bank-statement-parser

> **Demo project with synthetic data. Not client work.**
> The "banks", account numbers, merchants and amounts are invented and generated by `scripts/generate_samples.py`.

## Problem

Bank statements come as PDFs, and every bank lays them out differently (one signed amount column vs.
separate debit/credit columns, different date formats, wrapped descriptions, multi-page tables).
Bookkeeping wants one clean table — and wants to know whether the parsed numbers can be trusted.

## Approach

1. **Word coordinates, not text splitting** (`bank_parser/parser.py`): `pdfplumber` returns each word with
   its position. The table header row (`Date | Description/Details | Debit | Credit | Amount | Balance`)
   defines the columns; each amount-looking word is assigned to the header column whose right edge is
   nearest. This is what tells a debit from a credit when only one amount is printed on a row.
2. Handles: signed single-amount layout, debit/credit layout, `04 Jan 2026` and `DD/MM/YYYY` dates,
   description lines wrapped onto a second line, headers repeated on page 2, page footers, and
   `Opening Balance` / `Closing Balance` lines wherever they appear.
3. **Reconcile** (`bank_parser/reconcile.py`), using `Decimal` (no float rounding):
   - *row check*: previous printed balance + credit − debit = printed balance
   - *total check*: opening + Σcredits − Σdebits = closing
4. **Export** a Sheets-ready CSV: `date, description, debit, credit, balance, source_file, balance_check`
   — ISO dates, `.` decimals, no thousands separators, empty cell instead of `0`, UTF-8.

Samples in `samples/`:

| File | Layout |
|---|---|
| `statement_bankA_jan2026.pdf` | "Sample Bank A": signed `Amount` column, `04 Jan 2026` dates, 36 transactions over 2 pages |
| `statement_bankB_feb2026.pdf` | "Example Credit Union": `Debit` / `Credit` columns, `DD/MM/YYYY`, 24 transactions, long descriptions wrap onto 2 lines |
| `tampered/statement_bankB_feb2026_tampered.pdf` | Same as B, but one debit is printed with two digits swapped (14.21 → 41.21) to prove the checks fire |
| `truth_*.csv` | Generator ground truth, used by the tests |

Previews: [`bank A`](samples/preview_statement_bankA_jan2026.png), [`bank B`](samples/preview_statement_bankB_feb2026.png).

## How to run

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python scripts/generate_samples.py                      # recreate the synthetic PDFs
python -m bank_parser samples -o output                 # the two clean statements
python -m bank_parser samples/tampered -o output/tampered
python -m pytest -q
```

To use your own PDFs: `python -m bank_parser path/to/folder -o out` (new layouts may need small parser tweaks).

## What was measured

`pytest` (6 tests) compares every parsed row (date, description, debit, credit, balance) of both clean
statements — 60 transactions — against the generator's ground truth: all match. The tampered statement
is flagged on the total check and on exactly the one altered row.

As with any synthetic benchmark: the parser was written against these two layouts, so this shows the
pipeline works, not that it will read your bank's PDF.

## Limitations

- Only the two layouts above are tested. Other banks need header/column tweaks.
- Born-digital PDFs only; scanned statements would need an OCR step (not included here — see
  `invoice-pdf-extractor` for an OCR fallback pattern).
- Descriptions containing amount-like tokens near a numeric column (e.g. `1,200.00`) could be mistaken for amounts.
- Header names are matched in English (`Date`, `Description`/`Details`/`Narrative`, `Debit`, `Credit`, `Amount`, `Balance`).
- Single currency, one account per PDF; `CR`/`DR` suffixes and parentheses-negative formats are not handled.
- A tampered amount is *detected* and located (the row where the running balance breaks) but not corrected.
- Row checks compare against the *printed* previous balance, so a single bad amount produces one flagged row, while the total check also fails.
