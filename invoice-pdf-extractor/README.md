# invoice-pdf-extractor

> **Demo project with synthetic data. Not client work.**
> All vendors, people, addresses and amounts are invented and generated by `scripts/generate_samples.py`.

## Problem

Invoices arrive as PDFs in many layouts (some born-digital, some scans). Bookkeeping needs the same
few fields every time — vendor, invoice number, date, line items, totals — and a quick way to catch
documents whose numbers do not add up.

## Approach

1. **Get text**: `pdfplumber` reads the PDF text layer. If a page has (almost) no text, the page is
   rendered with PyMuPDF at 300 dpi and OCR'd with Tesseract (`pytesseract`, `--psm 6`).
2. **Rule-based parsing** (`invoice_extractor/extract.py`): regexes for invoice number / date / totals,
   a table-header-aware line-item parser (handles "Description Qty Price Amount" and "Qty Item Rate Total"
   column orders), vendor detection (`From:` label → company suffix → first non-title line), and
   US (`1,234.50`) and European (`1.234,50`) number styles.
3. **Validate** (`invoice_extractor/validate.py`): required fields present; `qty × unit = amount` per line;
   `sum(lines) = subtotal`; `subtotal + tax = total` (tolerance 0.01). Any failure → status `FLAGGED`
   with a readable reason.
4. **Export**: `invoices.json`, `invoices_summary.csv` (one row per invoice) and `line_items.csv`
   (one row per line item).

The four sample PDFs (`samples/`):

| File | Layout | Notes |
|---|---|---|
| `invoice_01_classic.pdf` | header left/right, `Description / Qty / Unit Price / Amount` | has a "Due Date" line that must not be mistaken for the invoice date |
| `invoice_02_modern_total_error.pdf` | `From:` block, quantity-first table, `Net / Sales Tax / Amount Due` | printed total is **deliberately 10.00 too high** to exercise validation |
| `invoice_03_european.pdf` | day-first date, `1.234,56` numbers, EUR, VAT, vendor right-aligned on the same line as the invoice number | |
| `invoice_04_scanned.pdf` | classic layout rasterised to an **image-only** PDF (slight blur + 0.4° skew) | forces the OCR path |

Previews: [`preview_invoice_01_classic.png`](samples/preview_invoice_01_classic.png),
[`preview_invoice_04_scanned.png`](samples/preview_invoice_04_scanned.png).

## How to run

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
sudo apt-get install tesseract-ocr        # only needed for image-only PDFs (macOS: brew install tesseract)

python scripts/generate_samples.py        # (re)create the synthetic PDFs + samples/expected.json
python -m invoice_extractor samples -o output
python scripts/evaluate.py                # compare against the generator's ground truth
python -m pytest -q
```

Without Tesseract the text-layer PDFs still work; an image-only PDF raises a clear error and the OCR test is skipped.

## What was measured

`scripts/evaluate.py` result on the 4 synthetic files: **36/36 checks matched** (7 fields + line-item count +
expected validation status per file), and `pytest` passes (17 tests).

**Read this number honestly:** the rules were tuned while developing against these same four files, and the
OCR sample is a clean, computer-rendered "scan". It shows the pipeline works end to end; it is *not* an
accuracy estimate for real-world invoices.

## Limitations

- Rule-based and layout-aware only for the patterns above; unseen layouts will need new rules.
- Single-line descriptions only (wrapped multi-line descriptions are not merged).
- All-numeric dates with `/` or `.` are assumed **day-first**.
- Single currency per invoice; discounts, shipping lines, multi-page tables and multiple tax rates are not handled.
- OCR quality on real phone photos / low-resolution scans is untested; Tesseract may misread digits, which
  is exactly what the arithmetic validation is there to catch (but it cannot catch errors that keep the sums consistent).
- English only (`eng` Tesseract language data).
